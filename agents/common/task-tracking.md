# Task tracking

Work is planned in the SQLite database `tasks/tasks.db` (sprint > task > subtask) and managed only
through `python3 scripts/tasks.py`; each change is one validated transaction (rolled back on error)
and re-renders the git-ignored view (`tasks/README.md` + one `tasks/sprint-*.md` per sprint) and the committed JSON snapshot `tasks/tasks.snapshot.json`.
Never edit them by hand. The view is regenerated by any change command or `tasks.py render`;
the committed backup is `tasks/tasks.snapshot.json`.
The base folder is detected via `git rev-parse --git-common-dir` (fallback: nearest `tmp/` ancestor with a
`.git`; override: `VIBE_TASKS_ROOT`), so agents in worktrees always use the main checkout's database.
The database is git-ignored and local. `scripts/tasks_init.py` creates a new empty one (schema from
scratch, refuses to overwrite without `--force`); `tasks.py` runs it automatically on the first change
when the file is missing, while read-only commands and `check` never create it.
A committed JSON snapshot (`tasks/tasks.snapshot.json`) backs up the DB state deterministically
(`sort_keys=True`, `indent=2`, trailing newline). Every change command re-writes it atomically
after the DB commit — on rollback nothing is written. Restore from a snapshot:
`tasks.py import-json tasks/tasks.snapshot.json`.
Explicitly update it with `tasks.py snapshot`.

- Statuses: `none` (brak), `in_progress` (w trakcie), `blocked` (bloker, needs `--reason`),
  `done` (gotowe), `cancelled` (anulowane), `review` (w przeglądzie, awaiting merge — counts as in
  progress, never offered by `next`). Aliases in Polish are accepted. Only leaves have a stored
  status; a task's and a sprint's status is derived (any blocked → blocked, all done or cancelled →
  done, any started or finished → in progress, else none).
- Every node has an immutable `uid` (`T-` + 4 base36) next to the display id; commands and `mv`
  accept either.
- Plan: `add-sprint "T" --goal G`, `add <sprint|task id> "T" -d desc -a assignee --after ids`.
- Work: `next [--assignee x]`, `start|done|reset <id...>`, `block <id...> --reason R`,
  `status <id...> <s> [--all]`, `note <id> "text"`, `edit <id...>`, `mv <id> <other-parent> [--pos N]` (not for reordering within one parent: ids encode the position),
  `rm`, `stats`.
- Cheap reads: `list [<id>] [--status --assignee --text --leaves --desc --notes]` (a positional id
  lists only that subtree), `show <id>... [--brief]`, `brief <id>` (description, deps with commits,
  spec/scope links, notes), `log [<id>] [--since <ts>]` (audit history).
- Overviews: `overview` (all sprints: status, counts per status, goal), `sprint-table <sprint>` (one table of a
  sprint's tasks); MCP `tasks_overview` and `tasks_sprint` are the same reads in one call.
- Batches: `plan-batch [--max N]` lists, in id order, the ready tasks of the first unfinished sprint whose `scope`
  links are pairwise disjoint (equal or nested paths overlap; `src/a` and `src/ab` do not). Ready tasks without a
  `scope` link are skipped with a warning on stderr; stdout stays `<id>  <title>` lines (or `no disjoint ready tasks`).
- Backup with history: `backup [--push] [--message M]` writes `snapshot.json` + the rendered view into a separate git clone
  (`BACKUP_DIR`, created by the first `backup`) and commits locally; every change command repeats the local commit once
  the clone exists. Nothing is pushed unless `--push`. Git failures are reported as `warning: backup: ...` on stderr and
  never abort the change. `restore [--pull]` replaces the database from that clone: use it for disaster recovery with
  history; `import-json tasks/tasks.snapshot.json` is the repo-local alternative (latest state only).
- Structured links: `link <id> <kind> <value>` / `unlink <id> <kind> <value>` with kinds
  `spec patch runner model agent commit branch fixes scope`; `show` and the view print them, and
  every change is written to the `events` audit log (actor `$VIBE_ACTOR`/`$USER`).
- `rm <id>... [--yes] [--dry-run]` always previews to stderr, asks for confirmation on a TTY
  (refuses with exit 2 otherwise), writes a recovery copy to `tasks/removed/` and refuses while
  others depend on it. Over MCP, `tasks_remove` is two-step: call it without `confirm` for the
  preview, then again with `confirm=true` to delete.
- `restore-removed <file> [--parent <id>]` re-inserts a saved subtree with fresh ids (dependencies
  are restored only when the target id still exists, otherwise listed as skipped).
  (`<id...>` accepts one or more ids; `edit`/`status`/shortcuts apply the same change in one transaction;
  `--title` with multiple ids is rejected; `mv` renumbers the whole subtree and rewrites deps/notes).
- Mark the task `start` before delegating it; `done` is set by `worktree.sh merge` (or by hand for non-delegated work) after the three Rules checks.
- `check` (also run by `pre-push`) fails when the data is invalid, the tasks/ view is stale, or the
  snapshot is missing/out of sync. When the view is missing (e.g. after a fresh checkout), `check`
  regenerates it silently and prints `tasks OK (view regenerated)`. If the DB does not exist,
  `check` skips all comparisons. Tests (CLI and MCP): `python3 -m unittest discover -s scripts -p "test_*.py"`.
